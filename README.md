# Human-Gated Agent Harness

A working setup where the human controls every phase of agent work, and a template to copy into other projects. The workflow itself is defined in `AGENTS.md`; this file covers how the pieces fit together, setup, and reuse.

## How it works

`AGENTS.md` is the single source of the rules. This section only maps where each piece lives, when it enters the agent's context, and how a change moves through it.

### Layout

```
AGENTS.md                  rules: choosing the path, the workflow and its stops, guardrails, git
plans/<name>.md            a Small change: Brief, Tasks (each with Verify:), Review fixes
openspec/
  config.yaml              project context and per-artifact rules for Large changes
  changes/<name>/          a Large change: proposal, specs, design, tasks
  changes/archive/         finished changes
.claude/
  settings.json            deny and ask rules, and the PreToolUse hook
  hooks/guard.sh           runs before every Bash call
  skills/                  brief, explain-back, handoff, orca-delegate, ponytail-review, tdd, wait-what
  commands/opsx/           propose, apply, archive, update (generated by OpenSpec)
```

### Layers

| Layer | What it does | When it costs context |
| --- | --- | --- |
| `AGENTS.md` | The map: Small or Large, the stops, guardrails | Every session, every turn |
| Skill and command descriptions | Tell the agent which skills exist and when to use them | Every session. `brief`, `handoff` (`disable-model-invocation`) and `opsx:update` (once `.claude/settings.local.json` sets `skillOverrides`, step 3 of `HARNESS-SETUP.md`) are left out until the human calls them |
| Skill and command bodies | Step-by-step instructions for one step of the workflow | Only while that step runs |
| `openspec/config.yaml` | Context and rules the `opsx` commands read | Only during `/opsx:*` |
| `.claude/settings.json` and `guard.sh` | Hard limits, enforced by Claude Code, not by the model | Never; they run outside the model |

### Flow

```
Human: /brief <what, or an issue link>     loads skills/brief
  agent stops when the previous change has uncommitted work or an open PR/MR,
  reads the code, openspec/specs/, and open changes read-only, drafts a missing why
  or done-when as (proposed), finds the root cause of a bug (Cause: with evidence),
  asks at most three questions, proposes Small or Large (risky areas are always Large)
■ Stop 1: human confirms the brief (What, Why, Out of scope, Done when), the planned flow
  (a data flow diagram with no code names and at least one ✗ failure path, or "none"
  when no data moves), and the size
  ├─ after ok the agent cuts feat|fix|chore/<name> from an up-to-date main
  ├─ Small: the same message lists the tasks (a bug starts with a failing test);
  │         after ok the agent writes plans/<name>.md
  │         (with the planned flow under ## Flow),
  │         builds, and ticks a task only after its Verify passes
  └─ Large: /opsx:propose <name>           loads commands/opsx/propose.md and openspec/config.yaml
            design.md carries the flow diagram
            ■ Stop 2: human approves the plan summary and its flow
            orca-delegate starts a worker that runs /opsx:apply;
            the coordinator answers it and checks its files against Ownership
Build ends with the project's Verify: line from AGENTS.md, when it has one
Review: /code-review low (Small) or medium (Large), then /ponytail-review
  confirmed correctness findings go under ## Review fixes and back to Build (two rounds at most)
  design, scope, and deletion findings wait for Stop 3
/explain-back <name>                        loads skills/explain-back
  one screen in the human's language: before/after summary, the actual flow (no code names),
  one example input traced through it, a planned-against-actual table (✓ ⚠ + − with file:line),
  decisions, pending findings (each flow difference is one); the human retells the flow
■ Stop 3: human retells the flow, asks questions, and picks findings (picked ones go back to Build)
  wait-what re-pitches anything that did not land
Done: Large runs /opsx:archive <name> and picks "Sync now" and commits it; then push, PR/MR with
  auto-merge, the agent watches the pipeline and reports; after the merge it cleans up the branch
```

`handoff` sits outside the flow: the human calls it to move work to a new session, and it records the last stop passed.

### Context

A long session dilutes the model's context and costs more tokens. The agent cannot measure its own context or type `/clear`, so `AGENTS.md` has it suggest a reset at fixed points; the human runs the command, and can check usage with `/context` at any time.

| When | Where the state is | Use |
| --- | --- | --- |
| After the human says done | In the plan and the PR | `/clear` |
| After Stop 2 on a Large change | In `openspec/changes/<name>/` | `/clear`, then type: "Build `<name>`; Stop 2 is approved." |
| Mid-Build, mid-Review, or at Stop 3 with findings half decided, when the session is long | Partly in the conversation only | `/handoff`, then paste the line it ends with into the new session |

### Git

```
main ──●──────────●──────────●────  production: every merge deploys
       ↑ MR/PR    ↑ MR/PR    ↑ MR/PR   auto-merge once the verify jobs pass, then the deploy job runs
     feat/a     fix/b      feat/c      one change at a time, each cut from main after the previous merge
                                        (only a fix/ for broken production may start while another is open)
```

A change, start to finish:

```bash
git switch main
git pull --ff-only
git switch -c feat/<name>
# small commits, one per verified task: "feat: <task>", "fix: <task>", "chore: <task>"
git push -u origin feat/<name>                                # after you say done; asks for approval
glab mr create --target-branch main --fill --yes && glab mr merge --auto-merge --squash  # GitLab
gh pr create --base main --fill && gh pr merge --auto --squash # GitHub
glab ci status --live   # GitLab: watch the pipeline
gh pr checks --watch    # GitHub: watch the pipeline
# after it merges
git switch main && git pull --ff-only && git branch -D feat/<name>
```

When a deploy breaks production, roll back with a change like any other: `git revert -m 1 <merge commit>` on a `fix/` branch, then the same PR or MR steps. For a squash merge, drop `-m 1`.

The pipeline on the MR or PR runs the verify jobs; when they pass, it merges by itself and the pipeline on `main` deploys. When they fail, the agent fixes it on the same branch. The rule is the Git section of `AGENTS.md`; step 5 of `HARNESS-SETUP.md` checks the CI config, and step 7 lists the GitLab and GitHub settings you turn on.

## Token cost

Where a change spends most of its context, largest first:

- **Generated `opsx` commands.** `.claude/commands/opsx/propose.md` and `archive.md` run to about 170 and 265 lines, much of it for OpenSpec stores and branches this harness never takes. A Large change loads propose, apply (in the worker), and archive. `openspec update` regenerates these files, so trimming them by hand does not last.
- **`/code-review` level.** `AGENTS.md` pins it to `low` for Small and `medium` for Large; a higher level starts many reviewer subagents, so raise it only for a risky change.
- **The worker on Large.** The worker reads the change folder from scratch, and the coordinator spends turns answering it.
- **Skill descriptions.** Loaded every session, including account and built-in skills outside this repository. Step 3 of `HARNESS-SETUP.md` hides the ones this harness never needs through `skillOverrides` in `.claude/settings.local.json`; hide more there or in `~/.claude/settings.json`.
- **The diff, read three times.** `/code-review`, `/ponytail-review`, and `/explain-back` each read it.

## One-time machine setup

- Linux or macOS with `bash` and `jq` (the guard hook needs both).
- Node.js 20.19 or newer.
- `npm install -g @fission-ai/openspec@latest` (the `/opsx:*` commands call the `openspec` CLI).
- Optional, to delegate Build to another agent (Antigravity, Codex): the Orca app running with Orchestration enabled (Settings → Experimental). The coordinator then uses `orca orchestration` as described in the `orca-delegate` skill.
- Optional, personal token savings: `skillOverrides` in `~/.claude/settings.json` hides skills you never want Claude to start on its own.

## Reuse in another project

1. Copy `.claude/` (without `settings.local.json`), `AGENTS.md`, and `HARNESS-SETUP.md` into the new repository.
2. Open Claude Code there and ask it to read `HARNESS-SETUP.md` and follow it. The agent initializes OpenSpec, removes the extra files `init` generates, asks you a few questions about the project (what it is, its check command, constraints the code does not show), and deletes `HARNESS-SETUP.md` when it is done.
3. Restart Claude Code and run the checks below.

To upgrade a project that has an older harness, commit first. Then:

- Replace `.claude/settings.json`, `.claude/hooks/`, and every harness skill under `.claude/skills/`. Delete harness skills that no longer exist, such as `grilling`.
- Keep `openspec/` and `.claude/rules/`, and keep the project's own skills.
- Copy `AGENTS.md` and `HARNESS-SETUP.md`, and tell the agent this is an upgrade. It then merges the project text from the old `AGENTS.md` (in git) and cleans `settings.local.json`.

`HARNESS-SETUP.md` is the single source for these steps and for the `openspec/config.yaml` template; keep this repo's own `openspec/config.yaml` in sync with it.

## Check it works

- `/memory` lists `AGENTS.md` (Claude Code reads it only while no `CLAUDE.md` exists in the project or above it, so never run `/init`).
- `/skills` shows `opsx:update` as user-only and `opsx:propose`, `opsx:apply`, `opsx:archive` as available to Claude.
- In auto mode (`Shift+Tab`), a first `/brief` on a tiny change confirms the flow end to end: you only answer and say "ok" at Stop 1 and Stop 3 in `AGENTS.md` (a Small change has no Stop 2).
- In a session started with `claude --permission-mode bypassPermissions`, ask Claude to run `cat .env`: the hook blocks it. Then ask for `git push --dry-run`: an approval prompt appears.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `/opsx:*` reports `openspec: command not found` | The `openspec` CLI is not installed globally. | Run `npm install -g @fission-ai/openspec@latest`. |
| Claude Code does not follow `AGENTS.md` | A `CLAUDE.md` (for example one created by `/init`) exists in the project directory or above it, so Claude Code reads that instead. | Delete the `CLAUDE.md`, then run `/memory` and confirm `AGENTS.md` is listed. |
| A hidden skill shows up again or costs tokens | Its `skillOverrides` entry is missing, misspelled, or in the wrong settings file. | Open `/skills` and check its state. The template's entries (from step 3 of `HARNESS-SETUP.md`) are in `.claude/settings.local.json`; any others you add are in `~/.claude/settings.json`. If an account or built-in skill ignores the project entry, move it to `~/.claude/settings.json`. |
| Deleted skills or commands reappear after `openspec update` | The global OpenSpec profile is still `core` with delivery `both`, so `update` regenerates them. | Delete the regenerated files again, or change the profile with `openspec config profile` before running `openspec update` (an option; not yet tested). |
| Every shell command is blocked and the message names guard.sh | `jq` is missing, the hook timed out, or `bash` cannot run `.claude/hooks/guard.sh`, and `onFailure: block` fails closed. | Install `jq`. If it still blocks, run the hook by hand: `echo '{"tool_input":{"command":"ls"}}' \| bash .claude/hooks/guard.sh; echo $?` should print `0`; fix the error it prints. Changes to `.claude/settings.json` and `.claude/hooks/` are the human's. |

## Security model

| Layer | Stops | Can be bypassed by |
| --- | --- | --- |
| Deny rules in `.claude/settings.json` | Claude's file tools and recognized file commands reading `.env` and credentials, and editing `.claude/settings.json` and `.claude/hooks/` | A script that opens the files itself |
| `.claude/hooks/guard.sh` hook | Shell commands that name a `.env` path, and `git push` written in a form the `ask` rule does not match | A script or alias that hides the path or the push |
| Protected `main` (GitLab) or a ruleset on `main` (GitHub), with required pipeline | Any direct push to `main`, and any merge whose verify jobs fail (the only hard limit) | Only a repository admin who changes the rules |

Without an OS sandbox, a script can still read `.env`, so keep real secrets out of the working tree. Use auto mode for day-to-day work; switch on bypass permissions only for a long Build you leave unattended. Edits to `.claude/settings.json` and `.claude/hooks/` are the human's.

## Adding rules per project

Add a rule only after Claude repeats the same mistake in a project. Create `.claude/rules/<topic>.md`; the `paths` frontmatter is the only field Claude Code reads, and a rule without it loads every session.

```markdown
---
paths:
  - "src/api/**"
---
Validate every request body and return the shared error shape.
```

Rules guide behavior. Hard limits belong in `permissions` or hooks in `.claude/settings.json`, and mechanical mistakes (formatting, banned imports) belong in a linter or CI check.
